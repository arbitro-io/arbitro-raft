# Durable Raft Benchmark — Methodology (K3)

**Status:** design spec for approval — no implementation yet.
**Target:** `arbitro-raft/benches/raft_transport_bench.rs` (single bench, env-toggled; layout decision final).
**Synthesized from three independent design lenses:** industry-parity, durability-semantics, statistical-rigor. Conflicts between them are ruled in §6.
Every code claim below was re-verified against the tree at HEAD. Every claim about external systems (etcd, Dragonboat, openraft, hashicorp-raft) comes from training knowledge, shapes the design but not its correctness, and is marked **[verify]** — it must be re-confirmed against that project's source/docs before any published comparison row.

---

## 1. Goal & fairness contract

The durable bench is "fair and reliable" when a cell in our results table and a cell in a competitor's results measure **the same quantity under the same conditions**: (a) the same *load model* — C concurrent closed-loop clients over a fixed total of operations, not one blocking proposer and not a pre-agglomerated batch; (b) the same *completion point* — the client call returns at commit/apply, never at enqueue; (c) the same *durability scope* — every quorum-relevant node fsyncs real bytes of the real entry before its ack counts, not just the leader; (d) the same *steady-state discipline* — preallocated WAL extents so fdatasync never pays file-growth metadata, warm-up excluded, no first-write artifacts; and (e) the same *metrics* — throughput plus per-op p50/p99(/p999), not batch-mean medians. Anything published carries its exact conditions inline, and a cross-system row exists only when both sides were measured on the same host with each system's own tool in its closest-matching mode. Grounding facts: the two C-D1 durability seams are `save_hard_state` and `append_entries` (`src/traits/storage.rs:57-67`; contract at `:6-28`, group-commit across calls explicitly permitted `:26-28`); the engine calls `append_entries` once per proposed batch (`src/api/node/replication/propose/initial.rs:103`), before the network fan-out (`propose/mod.rs:48-50`); leader self-ack counts toward quorum (`quorum.rs:53`); the bench followers currently have no storage seam at all (`raft_transport_bench.rs:264-332, 360-406`).

## 3. Durable BenchStorage design

### 3.1 WAL files and lifecycle
One segment file per node (`node1.wal`, `node2.wal`, `node3.wal`) in `ARBITRO_BENCH_WAL_DIR`, created **once per process**: zero-filled to `SEGMENT_MIB` (forces real extents — `set_len` alone leaves sparse extents that reintroduce allocation metadata on first touch), `sync_all`'d once, then reused. Each new cluster's writer (clusters are rebuilt per Criterion sample, `raft_transport_bench.rs:917-928`) resets to offset 0 and overwrites in place; on overflow the offset wraps and a wrap counter is reported at teardown. Rationale: an appending file grows its inode on every write, making fdatasync also journal metadata — nearly full-fsync price; etcd preallocates WAL segments precisely to keep steady-state fdatasync a pure data barrier **[verify]**, so without preallocation we would systematically overcharge ourselves. Preallocation and recycling are untimed by construction. Disk footprint: fixed 3 × 16 MiB regardless of run length (bench-safety bounded-work rule). Label on every durable number: "preallocated, wrap-around; segment-rotation cost excluded".

### 3.2 Record format
```
Record := len:u32le | crc32c:u32le | kind:u8 | body      (CRC over kind|body)
kind 0x01 ENTRY      body = term:u64le | index:u64le | payload bytes
kind 0x02 HARDSTATE  body = term:u64le | voted_for:u64le (0 = none)
```
CRC32C via `crc32fast` (dev-dependency only): I1 says anything disk-shaped should checksum (`storage.rs:30-43`), and every comparison target checksums per record — the (hardware-accelerated, small) CRC cost is part of the real WAL path being compared. An empty-payload entry still writes a ~25-byte record: real bytes of the real entry precede every barrier, so fsync-of-nothing is structurally impossible. The forbidden case is a sync with no bytes written, and it cannot occur.

### 3.3 Fsync placement at the seams
**Leader — `append_entries` (`raft_transport_bench.rs:139`):** serialize the whole batch into a reused scratch buffer → one `write_all` → one `sync_data`/`sync_all` per engine call → only then update the RAM `Vec` → `Ok`. One sync per engine call is exactly the group-commit granularity C-D1 permits (`storage.rs:26-28`) and is what makes the existing batch axis meaningful: x1 = one fsync per commit (etcd single-client worst case), x1024 = one fsync amortized over 1024 entries (G2 ceiling). The blocking write+sync is wrapped in `tokio::task::block_in_place` (legal: the bench runtime is multi-thread, 4 workers, `raft_transport_bench.rs:898-904`; `spawn_blocking` would add a per-op handoff).
**Leader — `save_hard_state` (`:134`):** same writer, one HARDSTATE record + sync, for contract completeness — and the spec says out loud that it is **off the steady-state path**: its only call sites are election/term transitions (`election.rs:39,276`, `node/mod.rs:820`), and `become_leader_for_benchmark` (`node/mod.rs:712`) does not persist. The measured durable seam is `append_entries` alone.
**Followers — the critical fix:** the bench followers ack from RAM today, so patching only `BenchStorage` would fsync 1 of the 2 quorum members — a leader-only-durable number that no target system publishes (etcd/TiKV followers persist before acking **[verify]**; the real arbitro-raft follower does too: append at `handler.rs:80`, ack sent only after the apply path returns). Design: each `PeerState` owns a `FollowerWal` (same writer, same segment discipline, same mode). In `follower_handle_frame`, **both arms** — `RaftMessage::AppendEntries(ae, body)` at `:363` and `RaftMessage::AppendEntriesSeeded{..}` at `:372` (both expose real payload bytes via their entry iterators) — write ENTRY records for the appended entries, perform **one sync per AE frame**, and only then call `encode_resp_frame`. The function stays shared verbatim by both transports, so inmem/tcp parity is preserved by construction. Resulting commit shape (3 nodes, quorum 2, leader append serialized before fan-out per `propose/mod.rs:48-50`):
`T_commit ≈ T_sync(leader) + min over followers(net + T_sync(follower) + ack)` — one leader sync and one follower sync on every measured commit; the slower follower's sync completes off the critical path, as in a real cluster.

### 3.4 Guards against fake barriers
(1) Startup filesystem check: resolve `WAL_DIR`, refuse durable modes on `tmpfs`, `ramfs`, `9p`, `overlay` (via `/proc/mounts` / statfs), naming the fs and the knob — no override env. (2) Calibration probe, always run and always published: 100 cycles of {overwrite the same 4 KiB at offset 0 + sync per mode}; report median/p95/max; refuse if median < 2 µs (no real barrier completes that fast; tmpfs does). The probe doubles as the per-run normalizer: `T_commit ≈ T_sync_leader + RTT + T_sync_follower` lets readers project onto their own measured disk. (3) Bytes-written accounting: after the first append, assert the writer offset advanced by the serialized size (the file-length check is unavailable under preallocation).

### 3.5 Reads stay in RAM; crash-recovery out of scope
`read_entries` / `entry_at` / `last_log_position` keep serving the in-memory `Vec` untouched — the standard WAL+RAM-index architecture (etcd serves steady-state reads from `raft.MemoryStorage`; the WAL is write-only until recovery **[verify]**). No target pays disk reads on the commit path; neither do we. The WAL is never read back: no replay, no torn-record handling, wrap destroys history by design. What the bench certifies is exactly: *the measured latency includes a real barrier over the real record bytes of every measured entry, on every quorum-relevant node, before any `Ok`/ack Raft's safety argument depends on.* Whether the bytes survive a crash is the fault-injection suite's jurisdiction (`tests/storage_faults.rs`); this bench prices durability, it does not verify it — published prose must never conflate the two.

### 3.6 Explicit-policy discipline (sec8 rule)
The policy is parsed from env **once** at bench wiring and passed to `BenchStorage::new(policy, scope, writer)` / follower constructors as explicit parameters — never read from env inside the storage, never defaulted deep in the stack. It is printed at startup and **stamped into the Criterion bench ID**: `fsync = none` keeps today's exact IDs (untagged = non-durable, preserving Criterion history for every number published so far); otherwise a path segment is inserted — `tcp/fsync-data/propose_once/1kb`, `tcp/fsync-data-leader/...` for scope=leader. This also prevents Criterion from "comparing" a durable run against the non-durable baseline as a fake regression.

## 4. Metrics & reporting

### 4.1 Three modes, three quantities (all published, only one is "their" number)
All three are operating points of the same closed queueing system (Little's law, X = C/E[T]):
1. **`propose_once` loop — label `wait, one-in-flight`.** Latency probe; throughput printed only as `1/latency, one-in-flight` — the floor. With fsync: one fsync per commit.
2. **`propose_batch_once` xB — label `batch-wait, single proposer`.** Per-round bandwidth with perfect free coalescing (one storage append, one frame, one round — `initial.rs:103`, `initial.rs:171`); no arrival process, no queueing. With fsync: amortization ceiling. Existing cells are empty-payload (`empty_x{1,64,1024}`), which fit the 64 KiB frame; they stay.
3. **NEW group `raft_transport_sustained` — label `closed-loop, C clients, pipelined leader, natural batching`.** This is the quantity etcd's `--clients`, Dragonboat's goroutines, openraft's tasks, and hashicorp's concurrent `Apply()` callers all measure **[verify each]** — C closed-loop client tasks work-stealing `TOTAL_OPS` from a shared atomic pool, each doing `ClientHandle::write_bytes` (`client.rs:114`, `Bytes` zero-copy) and recording its own per-op latency; driver = the documented tick-driver pattern (`run_once` loop until a stop flag). Batch size is **emergent** — whatever accumulated in the mailbox during the previous round's flight (run loop drains up to `append_batch_entries` per tick, `run.rs:314-324`) — so the fsync amortization ratio is emergent too, which is precisely the group-commit dynamics behind every published number. Modes 1 and 2 bracket it (x1+fsync pessimistic, x1024+fsync optimistic); neither can stand in for it. Supporting config per cell: `client_mailbox_capacity = max(8192, 2C)` (default 8192, `limits.rs:105`) so `Overloaded` never fires at bench depths (if it does: bounded yield-retry, counted, reported); frame-budget clamp `append_batch_entries = min(1024, (MAX_FRAME_SIZE − 4096)/(payload + 32))` (`wire.rs:15`; ≈57 at 1 KB, ≈207 at 256 B) so emergent batches always fit one deliverable frame — printed in conditions; per-op `tokio::time::timeout` (120 s → loud labeled failure, never a hang).

### 4.2 Tail capture
Criterion with `iter_custom` receives one duration per *sample* (a sum over `iters` ops); statistics over 10 batch means cannot produce per-op percentiles — a 100 ms stall inside a 600-op sample vanishes. Therefore: a preallocated `Vec<u64>` per-op recorder — always on in the sustained group (its output *is* the product), opt-in via `ARBITRO_BENCH_HIST=1` in the Criterion cells (off = loops byte-identical to today). Exact order statistics by sort (bounded n ≤ ~10^5 — no HDR dependency, zero binning error); report `x[ceil(p·n)]`, no interpolation.
**Gates (pre-registered so runs cannot be rerun-until-pretty):** publish quantile p only when `n ≥ 10/(1−p)` (p99 → ≥1000 ops, p999 → ≥10 000, else printed `n/a`, never extrapolated); first-half vs second-half p50 drift > 10% → `WARN drift`, run invalid for publication; Criterion median vs recorder p50 disagreement > 10% → invalid; `max` always published next to p99; no recorded op is ever dropped; one rerun allowed per invalidated run, both logs kept, reason stated.
**Coordinated omission, named:** closed-loop clients record one slow op where a fixed-rate arrival process would queue many — published tails are **service-time percentiles of closed-loop clients**, the same shape etcd's own tool publishes **[verify]**, so like-for-like — but never captioned "p99 under load". Open-loop pacing is honest future work, not faked.

### 4.3 Mandatory disclosure
One machine-generated context line at startup, tee'd, cited verbatim by every published cell:
```
BENCH_CONTEXT {"bench":"raft_transport_bench","transport":"tcp","fsync":"data","scope":"quorum",
"sync_call":"fdatasync","blocking":"block_in_place","wal_dir":"...","wal_fs":"ext4","segment_mib":16,
"prealloc":"zero-filled+recycled","probe_us":{"median":X,"p95":Y,"max":Z},"cluster":"3-node loopback,
single host, single physical device","timing_forced":"hb=500ms (gather 1s)","completion":"commit(+same-tick-noop-apply)",
"batch_clamp":57,"mailbox":8192,"env":"WSL2 <kernel>, <CPU>, rustc <ver>","date":"YYYY-MM-DD"}
```
Per cell: `TAILS id=<bench-id> n=… p50=… p90=… p99=… p999=…|n/a max=…` (Criterion cells, HIST=1) or `SUSTAINED transport=… fsync=… scope=… payload=… clients=… total_ops=… wall_s=… thr_ops_s=… p50_us=… p99=… p999=… max=…` plus full sorted latencies at `target/criterion/<id>/tails.csv`.
**Completion point, declared not altered:** every target returns after apply (etcd Put after MVCC apply; Dragonboat `SyncPropose`, openraft `client_write`, hashicorp `ApplyFuture` after SM apply **[verify each]**); ours returns at commit — `propose_once` at quorum-commit (`propose/mod.rs:66-97`), `ClientHandle` waiters notified one statement before `apply_committed_entries` in the same tick (`run.rs:342-347`). With `NoopSM`, apply is a per-entry no-op executed inside the measured window (throughput fully charges it; per-op latency omits at most one tick's noop). Label `completion=commit(+same-tick-noop-apply)`; notify-after-apply is an engine product question (flagged, §8), not a bench hack.

## 6. Where the three lenses disagreed — rulings

1. **Shape of the fsync knob.** Industry-parity: `none|data|full` (syscall). Durability-semantics: `none|nosync|data|full` (adds diagnostic). Statistical-rigor: `none|leader|quorum` (scope). These conflate two orthogonal axes. **Ruling:** two knobs — `ARBITRO_BENCH_FSYNC` (barrier type, keeping `nosync` as the write-path-cost diagnostic) and `ARBITRO_BENCH_FSYNC_SCOPE` (default `quorum`; `leader` kept as the decomposition cell statistical-rigor wanted). Headline = `data`+`quorum`. All three lenses' capabilities survive; no muddled enum.
2. **WAL lifecycle.** Industry-parity: fresh per-cluster tempdir, size computed from iters, cap 1 GiB. Durability-semantics: per-cluster 64 MiB etcd-shaped segment. Statistical-rigor: per-process 16 MiB segments, recycled across samples. **Ruling:** per-process recycled segments, `SEGMENT_MIB=16` default. Fresh-per-sample files re-pay first-write extent/journal mapping ten times per cell — exactly the cold-start cost the steady-state design excludes; recycling also fixes the disk bound at 3×16 MiB. etcd's 64 MB is their segment size, not a comparability requirement — the parity property is prealloc + overwrite-in-place. Consequence: the length-grew guard is replaced by the offset-accounting assert (§3.4).
3. **WAL dir default.** temp_dir() (two lenses) vs `$HOME/.cache` (one). **Ruling:** `$HOME/.cache/arbitro-raft-bench/wal`. `/tmp` is tmpfs on systemd-enabled WSL2 images and would only be caught by the refusal guard; a default that normally passes the guard costs nothing. The guard remains authoritative either way.
4. **CRC dependency.** Durability-semantics wants `crc32fast`; statistical-rigor said "no new dev-dependency needed". **Ruling:** add `crc32fast` (dev-deps only). The no-dep statement was about hdrhistogram — and that part stands (exact sort quantiles, §4.2). CRC per record is I1-shaped and cost-honest: every comparison target checksums; omitting it would undercharge us.
5. **Is the concurrency group required?** Industry-parity: yes — it is the only mode measuring "their" quantity. The other two lenses scoped themselves to the existing axes. **Ruling:** required. x1+fsync and x1024+fsync are envelope brackets (pessimistic/optimistic coalescing); no published competitor number is either. Without the sustained group the comparison table cannot be filled honestly — which is the user's exact ask. The existing cells stay as the published envelope.
6. **Where tails are recorded.** Opt-in `HIST` in Criterion loops (statistical-rigor) vs always-on in sustained (industry-parity). **Ruling:** both — sustained always records (its output is the deliverable); Criterion cells opt-in so legacy loops stay byte-identical when off.
7. **Stall protection.** Widened forced TimingConfig (durability-semantics) vs per-op 120 s timeout (industry-parity). **Ruling:** both — they protect different paths (`propose_*` gather deadline at `propose/mod.rs:58` vs sustained client futures). Forced timing disclosed in context.
8. **Sync-call framing.** Statistical-rigor mandated fdatasync only; durability-semantics kept `full` as a cell. **Ruling:** `data` is the headline (etcd parity **[verify]**); `full` retained as an optional strictness cell, labeled, never the comparison row.

## 8. Open honesty caveats (ship attached to every durable number)

1. **WSL2 vhd:** fdatasync reaches a virtualized disk (ext4-on-VHDX); the barrier is real but its cost is virtualized and it is **not evidence of power-loss durability**. Same-host cross-system runs stay fair (equally virtualized); absolute-vs-bare-metal comparisons do not. A production re-run requires: target data disk, disk model/interface, volatile-write-cache state, PLP yes/no, fs+mount options, same calibration block.
2. **Loopback, single host, single physical device:** all three WALs contend in one device queue (real clusters: one disk per node — direction conservative); no real network. Our numbers are comparable only to numbers measured the same way.
3. **Single raft group:** never comparable to any multi-group aggregate headline.
4. **Layer:** consensus core only — no client RPC hop, `NoopSM` apply, `completion=commit(+same-tick-noop-apply)`. Table row semantics: "replicated durable commit, consensus layer only"; competitor columns annotated with the layers their figure includes.
5. **Structural engine difference, footnoted not compensated:** this engine serializes leader append before fan-out (`propose/mod.rs:48-50`), so durable one-in-flight latency carries `T_sync(leader) + T_sync(follower)` end-to-end where etcd overlaps the leader write with replication **[verify]** (tracked engine item, MASTER_TODO G2 / AUDIT P2-5). Bias is against us; the bench measures the engine as it is.
6. **`save_hard_state` off the steady-state path** (election-only call sites): durable mode certifies the log-append seam per-op; term/vote durability is exercised at setup.
7. **Closed-loop service-time percentiles** (coordinated omission named); never captioned "p99 under load"; open-loop pacing is future work.
8. **Preallocated wrap-around WAL:** segment-rotation and recovery costs excluded; the bench prices durability and does not verify crash-recovery (that is `tests/storage_faults.rs` jurisdiction).
9. **Labels mandatory on every cell:** `wait, one-in-flight` / `batch-wait, single proposer` / `closed-loop, C clients, pipelined leader, natural batching`; throughput derived from x1 latency is labeled `1/latency`, never "capacity"; enqueue-only numbers do not exist in this design.
